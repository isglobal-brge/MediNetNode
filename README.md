## Overview

MediNetNode is a software that complements MedinetHub by providing a way to a centers manage their datasets and people who can acces, allow users to train their own models using the datasets uploaded to the Node and to monitor the models during training without sharing data.

## Features Available

- ✅ Manage and upload datasets
- ✅ Create and delete permissions for users to access and train on the datasets
- ✅ Models will always train with Differential Privacy to ensure security and more anonymization
- ✅ Three levels of permisions:
  - Admin: Can do everything
  - Researcher: Can just access to the platform using API, can train models using the datasets uploaded to the Node if they have the necessary permissions
  - Auditor: Can access to the platform and audit all the logs

## Future Features

- 🔄 Project creation: Assign a group of datasets to a specific group of people for a given date.
- 🔄 SVM and Random Forest federated with Differential Privacy (In progress)
- 🔄 More parameters to configure in your models like learning rate scheduler and other callbacks
- 🔄 Inference from pre-trained models. The researcher can send data to run a model directly to the node without needing to train and download it using API.

## Security Status

**MediNetNode v0.2 is SECURE for development environments.**

- ✅ Adversarial audit remediation **complete**: all code findings (CRITICAL/HIGH/MEDIUM/LOW) fixed or mitigated.
- ✅ ~1140 tests passing.
- 🔒 One item remains for **real clinical data over untrusted networks**: **mTLS on the Flower channel** (C3 — connection-time client authentication). In Docker the Hub already auto-generates TLS certs (server-side), so the channel is encrypted; mTLS adds client-cert verification. Until then, restrict the Flower port (8080) to invited hospital IPs by firewall/VPN.

For the full audit and per-finding fixes, see [docs/2026-07-04-auditoria-adversarial.md](../docs/2026-07-04-auditoria-adversarial.md); for the security overview see [SECURITY.md](MediNetNode-main/SECURITY.md).

## Deployment modes & security flags

The stack runs **out of the box in development** and switches to **deploy mode** by flipping a few env vars — no code changes.

| Mode | How | Posture |
|------|-----|---------|
| **Development** | `docker-compose up` (default) | `DEBUG=True`; fail-closed guards relaxed; `FLOWER_ALLOW_INSECURE=true`. Runs with zero configuration. |
| **Deploy** | Set `DEBUG=False` (Node) / `DJANGO_DEBUG=False` (Hub) + `ALLOWED_HOSTS`/`DJANGO_ALLOWED_HOSTS`; keep `FLOWER_ALLOW_INSECURE=false` | Fail-closed everywhere; SECRET_KEY + TLS certs auto-generated by the entrypoints; Flower channel uses TLS. |

Security flags introduced by the audit remediation (all have safe defaults; documented in [`MediNetNode/.env.docker`](.env.docker)):

- `FLOWER_ALLOW_INSECURE` — allow plaintext Flower transport (H5). `true` in dev, `false` in deploy (the Hub supplies the TLS CA to the Node).
- `DP_SECURE_MODE` — Opacus strict `secure_mode`. **Off by default and normally stays off**: the default DP noise is already drawn from a 63-bit **CSPRNG-seeded** generator (unpredictable without the secret, no extra dependency). `secure_mode=true` needs `torchcsprng`, which is unmaintained and incompatible with modern PyTorch — only enable if you deliberately pin torch 1.8.
- `DJANGO_ALLOWED_HOSTS` (Hub) — **required** when `DJANGO_DEBUG=False` (no wildcard fallback).
- `DP_FALLBACK_TARGET_EPSILON`, `DATASET_MAX_FILE_SIZE`, `INFERENCE_MAX_UPLOAD_SIZE`, `TRUSTED_PROXIES` — tunables with sane defaults.

> To harden a deploy for real patient data: (1) set `DEBUG=False` + hosts, (2) add mTLS (or firewall the Flower port to invited hospitals) to close C3, (3) set `TRUSTED_PROXIES` if behind a reverse proxy. The DP noise is already CSPRNG-seeded, so no `torchcsprng`/`DP_SECURE_MODE` is required.
